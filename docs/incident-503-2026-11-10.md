# ตรวจ HTTP 503 ระหว่างรับเอกสาร — 10 พฤศจิกายน 2026

เผยแพร่ชุดลดภาระและตรวจผลรับกลับแล้ว บนแพ็กเกจ Free เวลา 10:24 น. ไทย วันที่ 10 พฤศจิกายน 2026 ยังไม่รับรองว่า HTTP 503 ทั้งระบบหมดไป

## สถานะที่ยืนยันได้

Cloudflare GraphQL ของ Worker `doc-tracking-system` ช่วง 9–10 พฤศจิกายนก่อนแก้พบ 3,693 successful requests, 356 exceededResources และ 5 clientDisconnected ข้อผิดพลาด resource คิดเป็นประมาณ 8.8% ของ 4,054 requests ในช่วงที่ query กำหนด ไม่ใช่สัดส่วนเฉพาะปุ่มรับเอกสาร

เวลาของ exceededResources มี CPU p50 10,000 microseconds (10 ms) และ p99 13,063 microseconds ขณะตรวจ production ใช้ version `c01e7fc3-c65e-48dd-b8d1-d60349d4ac5a` ที่ deploy วันที่ 9 พฤศจิกายน

Live tail แบบอ่านอย่างเดียว 45 วินาทีพบ `/api/notifications` ที่ล็อกอินแล้วตอบ 200 ใช้ CPU 14 ms จากนั้นมีคำขออีกครั้งตอบ 503 outcome `exceededCpu`, CPU 10 ms, wall time 566 ms API นี้ไม่ซิงก์ Google Sheets จึงยืนยันว่าการลดงาน Sheets อย่างเดียวไม่เพียงพอต่อการแก้ 503 ทั้งระบบ

[ข้อจำกัด Cloudflare Workers](https://developers.cloudflare.com/workers/platform/limits/) ระบุ Free CPU limit 10 ms ต่อ invocation เป็นข้อจำกัดการประมวลผลแยกจากพื้นที่ Supabase การที่บางคำขอสำเร็จเกิน 10 ms ไม่ใช่หลักฐานว่าไม่ติดเพดาน

## เอกสารในภาพ

ตรวจฐานข้อมูลจริงใน transaction READ ONLY พบใบ `2026-11/189`, เลขเอกสาร `CGH6911-0090` มีสถานะ `closed` และหลักฐานรับ 1 รายการ เวลา `2026-11-10T02:49:55.929Z` (09:49 น. ไทย) ไม่ได้แก้สถานะหรือลงนามซ้ำระหว่างการตรวจ

เลขเอกสารเดียวกันมีใบ `2026-11/126` อีกหนึ่งรายการที่ยัง `awaiting_inspector` และไม่มีหลักฐานรับ ต้องไม่สับสนกับใบในภาพ การพบสถานะปิดงานไม่ได้พิสูจน์ลำพังว่าคำขอที่ถ่ายภาพคือคำขอที่ commit สำเร็จ เพราะไม่มี request ID ของภาพ

ฐานข้อมูลขนาดประมาณ 19.7 MB ตาราง `google_sheets_sync_queue` และ writer lease functions ที่ library อ้างถึงไม่มีในฐานข้อมูลจริง จึงไม่เปลี่ยนงานซิงก์เป็น fire-and-forget หรือเปิดใช้ library คิวโดยถือว่ามี durable delivery อยู่แล้ว

## การแก้และการตรวจ

เตรียมการลดขอบเขตการอ่าน Sheets ตามวันที่รับ: เมื่อพบรหัสอ้างอิงในคอลัมน์ U ของวันนั้น จะไม่เรียก metadata หรือกวาดทุกแท็บ หากไม่พบหรือแท็บไม่มีจึงใช้การค้นประวัติแบบเดิม ข้อผิดพลาดที่ยังยืนยันไม่ได้ว่าไม่มีแถวจะไม่ทำให้ append เอกสารซ้ำ

เตรียมการตรวจหลักฐานจากเซิร์ฟเวอร์หลัง network error/HTTP 502/503/504 หรือผลสำเร็จที่อ่าน JSON ไม่ได้ โดยส่ง GET ตรวจกลับสูงสุดหนึ่งครั้งและมี deadline 5 วินาที ต้องตรงทั้ง recipient, บัญชีที่กด, ลายเซ็น, ผลตรวจ, หมายเหตุ, สถานะสุดท้าย และเวลาใหม่กว่าสถานะของผู้รับก่อนส่ง จึงแจ้งว่าสำเร็จ ถ้าตรวจกลับไม่ได้ให้คงข้อความยืนยันผลไม่ได้ ไม่ส่ง POST ซ้ำอัตโนมัติ และไม่เปลี่ยน HTTP 409 หรือ auth errors เป็นผลสำเร็จ

ไม่เปลี่ยน schema, สิทธิ์ role/department, RPC รับเอกสาร หรือหลักฐานธุรกิจ

ตามเงื่อนไขคง Free เพิ่มการลดคำขอแจ้งเตือนจากรอบ 30 วินาทีเป็น 60 วินาทีเฉพาะแท็บที่มองเห็น หยุดเมื่อ hidden และตรวจกลับเมื่อกลับมาดู พร้อมกันการเรียกซ้อน คิดเป็นการลด periodic polling 50% ในแท็บที่เปิดค้าง ไม่ใช่การลด CPU ของแต่ละ invocation 50%

Root รัน `npm run check` ก่อนเพิ่ม polling ผ่าน exit 0: Node tests 271/271 และ money tests 26/26 รวม 297 tests, ESLint ไม่มี warnings/errors, Next build 41 static pages และ typecheck ผ่าน Independent developer reviewer และ tester ผ่านก่อนรันรวม ตรวจ atomic receipt/RPC เดิมว่ายังคงหนึ่งหลักฐานและ HTTP 409 เมื่อกดซ้ำ

จากนั้นเพิ่ม visible-only polling ตามเงื่อนไขคง Free และรัน `npm run check` รอบสุดท้ายผ่าน exit 0 อีกครั้ง: Node tests 277/277 + money tests 26/26 รวม 303 tests, ESLint, build 41 static pages และ typecheck ผ่าน Build ID ของ Next/standalone ตรงกัน `fHxJ-ZNjLNLPvAUfLs_4A` บรรจุด้วย OpenNext จาก standalone ชุดนี้

## เพดาน hosting

ผู้ใช้กำหนดให้คง Free และยังไม่สะดวกจ่าย จึงไม่เปลี่ยนแพ็กเกจหรือขออนุมัติ Paid ในรอบนี้ การปรับโค้ดเฉพาะจุดไม่รับประกันว่า Next.js/auth จะใช้ CPU ต่ำกว่า 10 ms ทุก invocation

ทางเลือกตามงบคือสำรวจการให้ API ที่จำเป็นผ่าน runtime ที่เบากว่า Next.js โดยยังใช้ Cloudflare/Supabase เดิม หัวหน้าทีมพัฒนาเป็นผู้วิเคราะห์ขอบเขตและ root ตรวจการออกแบบก่อนลงมือ เกณฑ์คือ auth/active profile/department access และ atomic RPC ไม่ลดลง, ไม่เปิด service-role key ให้ browser, ไม่ทิ้งงาน Sheets, วัด CPU และ HTTP outcome กับ workload เดิมก่อนสรุปผล งานนี้ยังเป็นการสำรวจ ไม่ใช่ API ใหม่ที่ปล่อยแล้ว

แนวทางที่เหมาะสำหรับ proof of concept คือ same-origin custom Worker intercept `/api/notifications` ก่อน Next middleware/handler แล้ว fallback ไป OpenNext สำหรับหน้าและ API ที่เหลือ [OpenNext รองรับ custom Worker](https://opennext.js.org/cloudflare/howtos/custom-worker) แต่ต้องตรวจ bundle graph ว่า framework หนักไม่ได้โหลดก่อน fast path และทดสอบ cookie refresh, active profile, department และ KV ด้วย การส่ง service binding หลังผ่าน Next ไปแล้วไม่ลบ CPU ที่ Next ใช้ไป จึงยังไม่ถือเป็นการแก้เพดาน

Root รับผิดชอบวัดหลังปล่อย mitigation ด้วย live tail แบบจำกัดเวลาและ smoke checks ภายในรอบ release นี้ รายงานต้องคงผลที่ยังชน CPU ตามจริง ไม่ใช้ sample ที่ไม่มี error จำนวนเล็กน้อยรับรองว่า 503 หายทั้งระบบ

Cloudflare connector ต้อง reauthenticate แต่ Wrangler บัญชี `store-hk@hillkoff.com` ยังอ่าน deployment/settings/GraphQL ได้ ส่วน historical Workers telemetry และ subscription APIs ตอบ 403 จึงใช้ GraphQL กับ live tail ประกอบ ไม่ขยายสิทธิ์เอง

วันที่เดียวกัน ผู้ใช้อนุมัติให้ root ลงมือเองโดยไม่เรียก agents และเผยแพร่ notification Worker แล้ว ดูผลเทสต์ รุ่น deploy และ CPU ก่อน/หลังพร้อมข้อจำกัดใน [รายงาน notification Worker](notification-worker-free-2026-11-10.md) เส้นทางรับเอกสารยังใช้ Next.js เดิม
